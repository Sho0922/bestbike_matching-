# 非機能要件・技術方針 — BestBike × 教習所マッチング

版数 **v1.1** ／ 2026-08-04

> **v1.0 からの主な変更**
> ① 特典の保護対象を「入会確定時の1種」から **「卒業時の2種＋利用回数」** に変更
> ② 地図の位置づけを変更（一覧に地図なし／詳細のみ Google 地図）
> ③ **免許証画像の取扱い**（P-2 §5）を追加
> ④ **クーポンの不正利用対策**（P-2 §6）を追加
> ⑤ 中抜き対策のトリガーを「入校確定」から **「卒業」** に変更

## 1. 技術スタック

### 1.1 選定

| レイヤ | 採用 | 理由 |
|---|---|---|
| フロント / サーバ | **Next.js 15（App Router）+ TypeScript** | SSR による SEO。教習所詳細ページは検索流入が生命線 |
| スタイル | **Tailwind CSS** | プロトタイプの資産をそのまま活かせる |
| DB / 認証 / ストレージ | **Supabase（PostgreSQL 15）** | RLS を最終防衛線に使える。認証・ストレージ込みでインフラ構築を圧縮 |
| ホスティング | **Vercel** | Next.js との親和性。PRごとのプレビュー環境 |
| メール | **Resend** | React Email で型安全にテンプレートを書ける |
| 地図 | **Google Maps Embed API**（詳細ページのみ） | §1.3 |
| 住所補完 | **zipcloud / 日本郵便データ** | 郵便番号からの住所自動補完（AC-F-3） |
| 監視 | **Sentry** ＋ Vercel Analytics | |
| CI | **GitHub Actions** | lint / typecheck / test / build |
| E2E | **Playwright** | 主要導線の回帰 |

### 1.2 この構成にした理由

1. **API サーバを分けない**。数万規模までは Route Handlers で足りる。
   分けた瞬間にデプロイ・認証・型の同期という3つの継続コストが発生する。
2. **RLS を持つ DB を選ぶ**。「他校の申込者情報が漏れない」が生命線であり、
   アプリ層の実装ミスがそのまま漏洩にならない構造が要る。
3. **プロトタイプの Tailwind 資産を捨てない**。デザイン工程を圧縮できる。

### 1.3 地図の扱い【v1.0 から変更】

P-1 §1 は一覧での地図利用を明確に否定している。

> 地図に関しては「現在地」から拾う必要はないと思っています、電車等で見ることを想定。

P-1 §2 は詳細ページに Google 地図表示を要求している。

| 画面 | 地図 | 理由 |
|---|---|---|
| 一覧 | **なし**（都道府県→市区町村の階層ナビ） | P-1 §1。SUUMO型 |
| 詳細 | **Google Maps Embed API** | P-1 §2 |

| 案 | 費用 | 判断 |
|---|---|---|
| **Maps Embed API** | **無料** | **採用**。詳細ページの位置表示だけならこれで足りる |
| Maps JavaScript API | $7/1,000ロード | ピンのクリック等が必要になったら移行 |

> 一覧で JavaScript API を使わないことで、**地図コストがほぼゼロになる**。
> v1.0 の見積にあった地図費用は不要。

### 1.4 位置情報を要求しない

`navigator.geolocation` を**呼ばない**（AC-L-3）。
位置情報の取得は、権限ダイアログによる離脱・プライバシー上の説明責任・
iOS Safari での挙動差という3つのコストを生むが、P-1 の設計ではその見返りがない。

## 2. セキュリティ

### 2.1 【最重要】特典情報をクライアントに漏らさない

マイページの特典カードは `status = 'graduated'` のときだけ表示される。
この出し分けを **CSS や条件付きレンダリングだけで実装してはならない**。

| 層 | 実装 | 役割 |
|---|---|---|
| 表示層 | `{status === 'graduated' && <CouponCard/>}` | UX |
| **API層** | `graduated` 以外は `coupons` キーを**レスポンスに含めない** | **防御** |
| **DB層（RLS）** | `coupons` は `user_id = auth.uid() AND status='active'` のみ返す | **最終防衛線** |

卒業していない申込に対して API がクーポンコードを返してしまうと、
DevTools のネットワークタブを開くだけで、**教習所に通わずに 5,000円OFF と永久10%OFF が手に入る**。

`03_data-model.md` §4.2 の RLS ポリシーは、この事故を防ぐために存在する。

### 2.2 クーポンの不正利用対策（P-2 §6）

> P-2 §6：「メールアドレスのローカル部分」や「生年月日＋メールアドレス」は
> 推測されやすく、個人情報も含むため危険です。

| 脅威 | 対策 |
|---|---|
| コードの推測 | 暗号論的乱数による8文字採番（`crypto.randomBytes`）。`Math.random` 禁止 |
| **コードに個人情報が含まれる** | P-1 §10 の代替案（メアドのローカルパート／生年月日）を**採用しない** |
| 総当たり | クーポン検証APIに 10 req/分/IP のレート制限。連続失敗でIPを一時遮断 |
| 使い回し | `max_uses` / `used_count` / `coupon_redemptions` で回数を管理 |
| 期限切れの利用 | `expires_at` をサーバ側で検証 |
| 教習所による横流し | `coupons` に `school_staff` の RLS ポリシーを作らない。卒業APIのレスポンスにも含めない |
| 卒業の取消後も使える | 差し戻し時に `status = 'revoked'` にし、本体へ失効を連携 |

### 2.3 教習所間のデータ分離

| 脅威 | 対策 |
|---|---|
| A校のスタッフがB校の申込を閲覧 | RLS `is_staff_of(school_id)` ＋ アプリ層の所属チェック（二重） |
| ID列挙による探索 | 主キーを `uuid`。権限外は **404**（403 ではない） |
| A校がB校の料金を書き換える | `school_tuition_fees` の RLS を `is_staff_of(school_id)` で `WITH CHECK` |

### 2.4 金銭・特典操作の保護

| 対策 | 内容 |
|---|---|
| MFA 必須 | `school_staff` / `platform_admin` は TOTP 必須。入校確定・卒業・差し戻しは MFA 済セッションのみ |
| 権限分離 | `school_staff.can_confirm` / `can_graduate` で担当者を絞れる |
| 冪等性 | `Idempotency-Key` 必須。24時間保持 |
| 行ロック | `SELECT … FOR UPDATE` で並行リクエストを直列化 |
| DB制約 | `UNIQUE(application_id, kind)` on `coupons`／`UNIQUE(application_id)` on `referral_fees` |
| 監査ログ | 操作者・IP・UA・前後状態。`UPDATE`/`DELETE` をDBロールから剥奪 |
| 確認ダイアログ | 発行内容と不可逆性を明示 |

### 2.5 教習所の自由入力欄

P-1 §2 の「特色」「備考」「自由記入欄」は教習所が自由に入力する。

| 脅威 | 対策 |
|---|---|
| 保存型XSS | React の自動エスケープ。`dangerouslySetInnerHTML` を全面禁止（ESLintで機械的に検出） |
| 改行の表示 | `white-space: pre-wrap` で表現する。HTMLに変換しない |
| 過剰な文字数 | 各フィールドに上限を設ける（特色 200字 / 備考 500字 / 自由記入欄 2,000字） |
| 外部リンクの混入 | URLは自動リンク化しない。HP欄のみリンクにし、`rel="noopener noreferrer"` |

### 2.6 免許証画像（第2段階・P-2 §5）

> P-2 §5：免許証画像は重要な個人情報です。保存するなら、閲覧権限、保存期間、
> 削除方法、暗号化などが必要になり、開発・運用負担が増えます。
> BestBike側で既にアップロード機能があるなら、そちらへ移動させる方がよいです。

**MVPでは実装しない。** 実装する場合の必須要件を先に定める。

| # | 要件 |
|---|---|
| L-1 | ストレージは非公開バケット。**署名付きURL（有効期限5分）**でのみ配信 |
| L-2 | 閲覧権限は**本人と `platform_admin` のみ**。教習所には見せない |
| L-3 | 保存期間を定め（例：会員確認完了後30日）、期限到来で自動削除 |
| L-4 | 保存時に暗号化（Supabase Storage の暗号化＋アプリ層での追加暗号化を検討） |
| L-5 | アクセスログを `audit_logs` に記録 |
| L-6 | 本人による削除導線を用意 |
| L-7 | アップロード時に画像以外のファイル形式を拒否。EXIFの位置情報を除去 |

> **推奨は P-2 のとおり、BestBike本体へ寄せること。**
> 免許証は本体の会員確認のためのものであり、本プラットフォームで持つ必然性が薄い。

### 2.7 一般的な脅威

| # | 脅威 | 対策 |
|---|---|---|
| S-1 | SQLインジェクション | ORM / パラメータ化クエリのみ。文字列連結SQLを禁止（CIでlint） |
| S-2 | XSS | React の自動エスケープ。`dangerouslySetInnerHTML` 全面禁止 |
| S-3 | CSRF | SameSite=Lax Cookie ＋ Origin 検証 |
| S-4 | 認証情報の漏洩 | Supabase Auth（bcrypt）。自前実装しない |
| S-5 | 総当たり | 認証に 10req/分/IP。5回失敗で15分ロック |
| S-6 | 個人情報の過剰露出 | APIレスポンスは必要な列のみ。`SELECT *` をそのまま返さない |
| S-7 | シークレットの混入 | `.env` を gitignore。Secret Scanning ＋ `gitleaks` を CI に |
| S-8 | 依存の脆弱性 | Dependabot ＋ `npm audit`。high 以上でPRをブロック |
| S-9 | 管理画面の露出 | `/admin` `/school` に `X-Robots-Tag: noindex` |
| S-10 | ログへの個人情報混入 | 氏名・住所・メール・電話をマスクするフィルタを必須化 |
| S-11 | 問合せフォームのスパム | reCAPTCHA ＋ レート制限 |

### 2.8 データ保護

| 項目 | 方針 |
|---|---|
| 通信 | TLS 1.2以上のみ。HSTS 有効 |
| 保管 | Supabase のディスク暗号化（AES-256） |
| バックアップ | 日次自動 + PITR（7日間）。四半期に1度、復旧演習 |
| 保持期間 | 申込データは卒業/終了から**5年**。以降は匿名化して統計のみ保持 |
| 削除請求 | `users` の個人情報列を匿名化。`applications` は統計用に残す |

## 3. 事業リスクへのシステム対応

### 3.1 【最大の事業リスク】卒業登録の漏れ

紹介料の発生が **教習所の自発的な操作**に依存する構造は v1.0 と同じだが、
**トリガーが「卒業」に変わったことでリスクが増大した**。

理由：仮申込から卒業までのリードタイムが長い（2〜3ヶ月）。
その間に担当者が代わる、忘れる、そもそも卒業を記録する習慣がない、が起きる。

| # | 施策 | 実装 |
|---|---|---|
| L-1 | **教習中の長期滞留アラート** | `in_training` のまま標準期間（免許種別ごと）＋30日を超えた申込を運営ダッシュボードに一覧表示 |
| L-2 | **ユーザー側の卒業申告導線** | マイページに「卒業しましたか？」を表示。「はい」で運営にフラグ |
| L-3 | **仮申込の長期未処理リマインド** | `provisional` のまま5営業日超で教習所へ自動リマインド（3日に1回まで） |
| L-4 | **卒業率の異常検知** | 校ごとの `graduated / entry_confirmed` 比率が全体平均を大きく下回る校を月次抽出 |
| L-5 | 契約による裏付け | 提携契約書に「卒業時に卒業操作を行う」義務を明記 |
| L-6 | **月次の突合レポート** | 教習所へ「今月の入校者N名／卒業登録M名」を送り、差分の確認を求める |

> **L-1・L-2・L-3 は Phase 1 に入れる価値がある。**
> ユーザーにとっても、卒業が記録されなければ特典が受け取れない。
> **ユーザーと運営の利害が一致している**ため、L-2 の申告導線は機能しやすい。

### 3.2 二重発行

§2.4 の三重防御（冪等キー・行ロック・UNIQUE制約）で対応。詳細は `04_api-spec.md` §4.4。

### 3.3 教習所の情報鮮度

料金が実態とズレると、ユーザーの信頼とともに景表法リスクが発生する。

| 施策 | Phase |
|---|---|
| 掲載情報に「最終更新日」を表示 | 1 |
| 教習所によるセルフ更新画面 | **1**（P-1 §5・MVP必須） |
| 90日更新のない校を運営ダッシュボードで警告 | 2 |
| 料金変更の履歴保存（`school_fee_revisions`） | 1 |

## 5. 法令・コンプライアンス

### 5.1 個人情報保護法

| # | 論点 | 対応 |
|---|---|---|
| C-1 | **第三者提供（第27条）** | 仮申込フォームで、当該教習所への提供に**個別の同意**を取得し、`consents` に版数・日時・IPとともに記録 |
| C-2 | **本人同意なき会員登録** | BestBike無料会員への自動登録に**独立した同意**を取得（P-2 §4 / 同意項目④） |
| C-3 | 利用目的の特定・通知 | プライバシーポリシーに「提携教習所への提供」「BestBike会員登録」を明記 |
| C-4 | 安全管理措置 | §2 のとおり |
| C-5 | 開示・訂正・利用停止請求 | 窓口を設置し30日以内に対応 |
| C-6 | 委託先の監督 | Supabase / Vercel / Resend を委託先台帳で管理 |
| C-7 | **免許証画像**（第2段階） | §2.6 の L-1〜L-7 を満たすまで実装しない |

> **C-2 は v1.0 になかった論点**。P-1 §3 の「ベストBikeでの無料会員に自動連携致します！」は、
> 同意なしに行うと個人情報保護法上の問題になる。
> 「自動連携します」という**告知**と、「同意します」という**チェック**は別物である。

### 5.2 景品表示法

| # | 表示 | リスク | 対応 |
|---|---|---|---|
| C-8 | **「永久10%OFF」** | 将来終了すると有利誤認 | 規約に変更・終了条件を明記し、表示から規約へリンク（確認事項I） |
| C-9 | **「初回5,000円OFF」** | 適用条件が不明確だと有利誤認 | 有効期限・適用対象・併用可否を明記（確認事項H） |
| C-10 | **「報酬額5%アップ」** | 条件・期間が未確定（確認事項K） | 条件が確定するまで**リンク誘導のみ**とし、数値を訴求しない |
| C-11 | 「女性教官が多数在籍」等の特色 | 実態と異なると優良誤認 | 教習所からの申告を根拠資料として保存。掲載前に運営が確認 |
| C-12 | 料金表示 | 総額表示義務 | 税込・税別を行ごとに明示。別途費用の存在を必ず併記 |
| C-13 | 特典の受取条件 | 「申込でもらえる」と誤認させると有利誤認 | **すべての訴求に「卒業時に」を明記**（AC-T-2 / AC-D-8） |

### 5.3 その他

| # | 論点 | 対応 |
|---|---|---|
| C-14 | **資金決済法** | 教習料金は本プラットフォームで収受しない（BR-10）。将来決済を持つ場合は収納代行／資金移動業の整理を先に行う |
| C-15 | 特定商取引法 | 本プラットフォームは仲介。事業者情報・連絡先・キャンセルポリシーを表示 |
| C-16 | **インボイス制度** | 紹介料の請求書は適格請求書の要件（登録番号・税率区分・税額）を満たす（確認事項A） |
| C-17 | 電子帳簿保存法 | 請求書データは検索要件（日付・金額・取引先）を満たして保存 |
| C-18 | 特定電子メール法 | 通知メールに送信者情報・配信停止導線。取引メールと広告メールを分離 |
| C-19 | **道路交通法** | 受講可能年齢を検証（普通・小型二輪16歳／大型二輪18歳）（AC-F-4） |

|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Supabase エンドポイント |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | クライアント用（RLS前提） |
| `SUPABASE_SERVICE_ROLE_KEY` | **サーバ専用**。クライアントに絶対に露出させない |
| `NEXT_PUBLIC_GOOGLE_MAPS_EMBED_KEY` | 詳細ページの地図。リファラ制限を必ず設定 |
| `RESEND_API_KEY` | メール送信 |
| `BESTBIKE_API_BASE` / `BESTBIKE_WEBHOOK_SECRET` | 本体連携のHMAC共有鍵 |
| `BESTBIKE_SYNC_MODE` | `webhook` / `csv`（`04_api-spec.md` §6.3） |
| `RECAPTCHA_SECRET_KEY` | 問合せフォームのスパム対策 |
| `CRON_SECRET` | Outbox / 日次バッチの認証 |
| `SENTRY_DSN` | エラー監視 |

> `SUPABASE_SERVICE_ROLE_KEY` は RLS を貫通する。
> `NEXT_PUBLIC_` を付けないこと、Server Component / Route Handler 以外から
> 参照しないことを、レビューで必ず確認する。
