作成 2026-08-04

---

## 1. 経緯

`docs/` の v1.0 は、企画資料（PDF）を参照できない状態で、
リポジトリにあった動作プロトタイプ（`src/App.js` 全10画面）から要件を逆算して作成した。

その後、以下2件のPDFを受領し、突合を行った。

| # | ファイル | 作成 | 内容 |
|---|---|---|---|
| P-1 | しょーくん宿題.pdf（3ページ） | Pages | **一次要件**。NORUZO宿題分。ユーザー／教習所／運営／システムの機能要件10項目 |
| P-2 | チャッピー追加.pages.pdf（3ページ） | Pages | **P-1のレビュー結果**。重要な修正点8項目＋添付資料とのズレ＋全体評価 |

### 結論

**プロトタイプは、企画資料と根本的に異なる業務モデルで作られていた。**
v1.0 の設計はプロトタイプ準拠だったため、同じズレを引き継いでいた。
本改版（v1.1）で、**P-1 / P-2 を正**として全ドキュメントを書き直した。

## 2. 【重大】業務モデルそのものの相違

### 2.1 特典の発行タイミングと種類

| | v1.0（プロトタイプ準拠） | **v1.1（PDF準拠）** |
|---|---|---|
| 発行タイミング | **入会確定時** | **卒業時（免許取得時）** |
| 特典の種類 | 1種類 | **2種類** |
| 内容 | 永年10%OFF | ① 初回 **5,000円OFF**<br>② 2回目以降 **永久10%OFF** |
| 送付方法 | マイページ表示 | **メール送信** ＋ マイページでワンタップコピー |
| 付帯訴求 | — | **シェアリングオーナーで報酬額5%アップ** |

P-1 §10 の原文：

> ご卒業おめでとうございます！ベストBikeからの卒業祝いです！
> 初回：5,000円オフ！ / 2回目以降：永久10%オフ！
> さらに、バイクを所有してシェアリングオーナーになると報酬額5%アップ！

**影響**：v1.0 の設計は「入会確定＝課金＋特典発行の唯一のトリガー」という
単一トリガーモデルで全体が組まれていた。実際は **入校確定** と **卒業** の
2つの重要イベントがあり、特典は後者に紐づく。データモデル・API・画面・
テストのすべてに影響する。

### 2.2 事業目的

| | v1.0 | **v1.1** |
|---|---|---|
| 目的 | レンタル顧客の獲得 | **レンタルユーザー ＋ シェアリングオーナーの獲得** |

P-1 の副題が「レンタルバイクユーザーと**シェアリングオーナー獲得**に向けて」。
シェアリング事業への送客も本プラットフォームの目的である。

### 2.3 紹介料

| | v1.0 | **v1.1** |
|---|---|---|
| 金額 | ¥5,000 / 件（確定事項として扱った） | **未定**（確認事項） |
| 発生時点 | 入会確定時 | **未定**（入校確定時 or 卒業時） |
| 課金方式 | 固定額 | **未定**（固定 or 料金に対する割合） |

**v1.0 の ¥5,000 は誤り。** これはプロトタイプ内の数値であり、PDFに紹介料の金額の記載はない。
むしろ P-1 の「5,000円」は**ユーザーへの初回クーポンの割引額**であって、紹介料ではない。
両者を取り違えていた。

P-2 §8 が、紹介料について未定として挙げている項目：

- 紹介料が発生する時点（入校確定時／卒業時）
- 金額が固定か、料金に対する割合か
- キャンセル時の扱い
- 締め日と請求書発行日
- 税込／税別
- 教習所側での確認・確定操作

## 3. 用語の統一（P-2 §1・§2）

### 3.1 「入会」→「入校」

> P-2 §2：教習所側の操作は「入会確定」ではなく、すべて「入校確定」が自然です。
> BestBikeへの登録だけを「会員登録」と呼ぶと混乱しません。

v1.0 は全編で「入会確定」を使用していた。**v1.1 で「入校確定」に統一**した。

### 3.2 ステータス

P-1 では 仮申込 / 申込承諾 / 入校待ち / 入校 / 教習中 / 卒業 が混在していた。
P-2 §1 の推奨に従い、以下に統一する。

| # | ステータス | v1.0 での対応 | 操作者 |
|---|---|---|---|
| 1 | **仮申込** | `submitted` | ユーザー |
| 2 | **入校確認中** | `under_review` | 教習所 |
| 3 | **入校確定** | `scheduled` に近い | 教習所（「入校」ボタン） |
| 4 | **教習中** | — （v1.0に存在しない） | 自動（入校日到来） |
| 5 | **卒業** | — （v1.0に存在しない） | 教習所（「卒業」ボタン）**← クーポン発行** |
| 6 | **キャンセル** | `rejected`/`withdrawn` | 教習所・ユーザー |

v1.0 の `confirmed`（入会確定＝終端）は、実際には **中間状態**だった。
その先に「教習中」「卒業」があり、事業上のゴールは卒業である。

## 5. 料金モデルの相違【重要】

### 5.1 免許種類は6種

| | v1.0 | **v1.1（P-1 §2）** |
|---|---|---|
| 種類 | 普通二輪MT / 普通二輪AT / 大型二輪 / **原付講習** | **普通二輪MT・AT / 大型二輪MT・AT / 小型二輪MT・AT** |

v1.0 は **小型二輪（MT/AT）が欠落**し、**大型二輪のMT/AT区分がなく**、
PDFにない **原付** を含んでいた。

### 5.2 料金は「希望免許 × 現在保有免許」で決まる

これが v1.0 最大のデータモデル上の誤り。

P-1 §2：

> 教習費用の最上列項目は「**希望免許**」「**現在お持ちの免許**」「料金」「備考」の４つ
> 別途費用の最上列項目は「詳細」「費用」「備考」の３つ

掲載例の「普通2輪MT (普通免許所持) 152,750円(税込)」が示すとおり、
**同じ希望免許でも、保有免許によって料金が変わる**（普通自動車免許を持っていると学科が免除され安くなる）。

v1.0 の `school_courses(license_type, price)` は保有免許の軸を持っておらず、
料金表を表現できない。**v1.1 で2テーブル構成に変更**した。

| テーブル | 項目 |
|---|---|
| `school_tuition_fees`（教習費用） | 希望免許 / 現在保有する免許 / 料金 / **税込・税別** / 備考 |
| `school_extra_fees`（別途費用） | 詳細 / 費用 / 備考 |

### 5.3 Excel形式の自由入力は採用しない

P-1 §2 は「教習所により体系が違うため、**エクセル形式で自由入力**をさせたい」としていたが、
P-2 §3 がこれを明確に否定している。

> 自由入力にすると、教習所ごとに表の形式が崩れ、スマートフォン表示や集計が難しくなります。
> 次の固定項目で「**行を追加できる表**」にするのが安全です。

**v1.1 は P-2 に従い、固定項目＋行追加型を採用**した。

## 11. v1.0 から引き継いだ設計判断

PDFと矛盾せず、かつ P-2 の指摘とも整合するため、v1.1 でも維持した設計。

| # | 設計 | 理由 |
|---|---|---|
| 1 | 金銭イベントの冪等性（冪等キー・行ロック・UNIQUE制約の三重） | 二重計上の防止。P-2 §8 の「教習所側での確認・確定操作」の前提 |
| 2 | クーポンコードの暗号論的乱数による採番 | P-2 §6 と完全に一致 |
| 3 | 個人情報の第三者提供の同意取得・記録 | 個人情報保護法 第27条。P-1/P-2 に記載はないが法令上必須 |
| 4 | RLS による教習所間のデータ分離 | 他校の申込者情報が漏れない構造 |
| 5 | Outbox パターンによる外部連携 | P-2 §4「連携に失敗した場合の処理」への回答 |
| 6 | 教習料金を本プラットフォームで決済しない | 資金決済法の論点回避。PDFにも決済の記載はなく整合 |
